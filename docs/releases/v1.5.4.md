# Topophany v1.5.4

Released November 2, 2026.

Topophany 1.5.4 adds a dedicated Cloudflare Tunnel connections read, tunnel
status assertions, shared Cloudflare request budgets and two paired diagnostic
templates. It also fixes numbered Tunnel colo names found in a real-account run,
and closes gaps where monitor streams could withhold evidence that was still
valid. Verify downloads against `SHA256SUMS.txt`.

## Changes since 1.5.3

- **Dedicated Tunnel connections.** `adapter.cloudflare.read:
  "tunnel_connections"` reads the documented connections endpoint with the
  existing Tunnel Read permission. It counts the nested sessions under each
  connector, not the connectors, and supports `expected_connections` and
  `expected_colos`. It never reports a `tunnel_status`; keep a separate `tunnel`
  read for that. An explicit empty inventory is zero sessions, while absent
  session lists and partial pages are monitor errors.
- **Tunnel status assertions.** `adapter.cloudflare.expected_status` asserts
  the `tunnel` read's reported status (`healthy`, `degraded`, `down` or
  `inactive`). A mismatch is `policy / tunnel_status_mismatch`, even when
  connection evidence is missing. Without the field, `ok` still means only that
  the read succeeded. The TUI editor offers the field for tunnel reads.
- **Shared Cloudflare request budgets.** API checks on one observer share an
  allocation from 900 requests per five minutes across the topology, whatever
  token they use. HTTP 429 and 5xx start a cooldown of 30 seconds to five
  minutes, and `Retry-After` or exhausted `Ratelimit` headers can extend it to
  one hour. A sample taken during cooldown sends no request and reports monitor
  error `api_rate_limited`, not an outage. Separate deployments and other API
  clients still draw on the same upstream quota.
- **Numbered colo names.** A real-account run on 2026-11-02 found that API
  locations such as `lax12` were discarded, so colo policies stayed unverified.
  Both Tunnel reads now map three ASCII letters plus an optional number (at most
  eight bytes) to the uppercase city code, such as `LAX`. Each session still
  counts: `lax08` and `lax13` are two sessions at one city. Local `cloudflared`
  colo policies still compare full connector location tokens.
- **Partial connector readiness.** When cloudflared's `/ready` reports a session
  but `/metrics` fails, the sample stays a monitor error but keeps the readiness
  count and connector ID, with `connector_ready: true` and `metrics_status:
  unavailable`. Views show the session alongside the metrics error and never
  fill missing counters with zero. Link thresholds are unchanged.
- **Paired diagnostics.** `topo templates cloudflare-diagnostics` and
  `topo templates mihomo-diagnostics` write fully paused topologies. The
  Cloudflare template compares a public entry, the local origin, the connector
  and both Tunnel API reads. The Mihomo template compares the controller, an
  explicit proxy listener, the system default path, the exit and DNS. The
  [diagnostics guide](https://github.com/WhitenWhiten/topophany/blob/v1.5.4/docs/DIAGNOSTICS.md)
  explains how to read each combination of results.
- **Shared Mihomo controller reads.** Worker and local-stream runners reuse a
  validated controller response for at most one second between checks with the
  same target, credential and transport. Each check still applies its own
  policies and redactions, and reuse never renews old evidence. Checks with
  `max_duration_ms` or a dynamic provider reference always read fresh.
  Provider reference documents may now hold 4096 members per provider within
  1 MiB.
- **Stream evidence continuity.** Streams publish renewed evidence deadlines
  before a reader's last copy expires. Before, an unchanged row could
  disappear between display updates. A client stream keeps its last valid
  snapshot, with its original deadlines, when a collector read finds no
  collector or times out. Authentication, identity and malformed responses
  still withhold evidence at once. `503 connection_rotating` now gets the same
  single one-second retry as `429 snapshot_busy`.

## Compatibility and upgrades

Existing 1.5.3 topologies, collector state, direct profiles and local stores
need no migration. Topology schema 1, batch and snapshot schema 3, checkpoint
schema 2 for external data, monitor protocol 1, `direct.schema=1` and the local
configuration API schema 1 are unchanged. No existing measurement contract
changes unless you add one of the new fields.

Upgrade collectors, workers and viewers before using `tunnel_connections` or
`expected_status`. Older versions reject both when they validate the topology.
Adding or changing `expected_status` starts a new measurement contract.

Upgrade workers to get colo normalization, shared request budgets, partial
connector readiness and shared Mihomo reads. A colo policy whose Tunnel uses
numbered locations may change from `unverified` to `matched` or `violated` once
the new worker reports. Check `expected_colos` against the city codes before
upgrading. Stored samples are not rewritten.

Upgrade the stream host's `topo` binary to fix stream publication and snapshot
retention. Consumers should keep honoring each value's own `valid_until`; a
retained snapshot is never served past its original deadline.

Rolling back to 1.5.3 requires no state conversion. Remove
`tunnel_connections` checks and `expected_status` fields first, because 1.5.3
refuses them. Rollback also removes the colo normalization, request budgets and
stream fixes. Upgrades from earlier versions must also follow the
[1.5.3 upgrade guidance](https://github.com/WhitenWhiten/topophany/blob/v1.5.4/docs/releases/v1.5.3.md#compatibility-and-upgrades).

The macOS companion has a separate release lifecycle. This release publishes
the `topo` command-line binaries; companion UI support is version-dependent.

## Acceptance scope

Automated tests use loopback servers, synthetic responses and sanitized captures
from the 2026-11-02 real-account run. They cover the new read's allowlisted
path, session counting, status precedence, colo normalization, quota sharing
and cooldown, partial readiness, snapshot sharing and cancellation, stream
renewal and snapshot retention. Tunnel response parsers have bounded fuzz
targets seeded with the live captures.

The real-account run used a registered cloudflared 2026.10.5 tunnel on two
observer hosts. The colo fix passed a separate four-assertion recheck on both
Tunnel reads. That run did not cover upstream 429/5xx cooldowns, pool health,
large inventory pagination or other cloudflared versions; see the record for
the full list of gaps. A new Mihomo workflow runs pinned v1.19.32 and v1.19.33
cores on Linux, macOS and Windows, with TUN capture in an isolated Linux
network namespace. Recorded receipts cover macOS arm64 and Linux arm64.
Cross-builds establish compilation for their targets, not production
deployment or hardware acceptance.

## Downloads

Choose `topophany_1.5.4_<os>_<arch>`: `.tar.gz` for Linux and macOS, `.zip` for
Windows. macOS is `darwin`; Apple silicon is `arm64`, and Intel or AMD 64-bit
systems are `amd64`. Each archive contains `topo` (`topo.exe` on Windows), the
license, the three READMEs and the changelog. `topo version` should report
`Topophany 1.5.4`. Source builds require Go 1.26.10 or newer.
