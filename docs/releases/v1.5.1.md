# Topophany v1.5.1

Released October 26, 2026.

Topophany 1.5.1 adds live viewer diagnostics, per-source HTTP consent for direct
profiles and scoped service availability. It also makes authenticated collector
aliases and delivery failures easier to diagnose. Verify downloads against
`SHA256SUMS.txt`.

## Changes since 1.5.0

- **Live viewer diagnostics.** `topo sessions` lists the viewers running on this
  machine, and `topo diagnose --session ID` prints the model behind one:
  observer, filters, selected collector, snapshot and cache state, transient
  notices and history errors. `--json` returns the same state. Each viewer
  keeps up to 64 error, retry and recovery events for 30 minutes, writes a
  private atomic session file with a 10-second lease and removes it on exit.
  If the optional session cache cannot be opened, the viewer keeps running and
  shows a notice; remote and terminal sessions still fetch live evidence.
- **Service evidence.** Service pages now report application availability,
  path reachability and worker online state separately. A remote access
  failure reads `ACCESS FAIL` and does not prove an application outage, a
  degraded path reads `PATH WARN`, a confirmed local failure reads
  `LOCAL FAIL`, and a local warning or recovery keeps its state. Host resource
  reports and adapter telemetry never establish application health. Set an
  HTTP application check's `availability_scope` to `local`, `remote` or
  `user_entry` to declare what its evidence means; `local` requires an
  observer on the service host and no remote path, and a loopback check on that
  host infers it. Cached, stale or unseen checks cannot supply scoped states.
- **Authenticated collector aliases.** Collector URLs that authenticate as one
  store become one outbox recipient with a persistent `collector_id`, ordered
  `alternate_urls` and migrated URL receipts. The worker fails over after
  gateway 5xx responses but not after POST authorization, throttling,
  configuration or storage-budget rejections. Different identities in an
  explicit alternate group fail closed, and independent collectors keep
  distinct identities even with the same display name.
- **Delivery diagnostics.** Delivery reports, snapshots, CLI and TUI evidence,
  and worker logs share structured stages and stable codes for DNS, TCP, TLS
  and response timeouts, connection closure, throttling with bounded
  Retry-After, authorization, configuration, storage backpressure and
  acknowledgement format or identity failures. A successful delivery retains
  its most recent failure for 30 minutes, and address failover keeps the
  failed request through later healthy rounds. Enriched telemetry stays within
  the existing heartbeat budget; arbitrary peer strings and payloads are
  omitted. The collector's ingress report publishes bounded rolling counts by
  handshake kind and never raw peer text.
- **Connection rotation.** A POST authenticated at the two-minute boundary
  finishes within a 15-second drain. HTTP/1.1 advertises close and HTTP/2
  sends GOAWAY; a deduplicated EOF is retried once while preserving every
  sample identity and timestamp.
- **Direct HTTP consent.** `allow_insecure:true` on a direct source permits
  HTTP for authentication, discovery and reads on LAN or Tailscale addresses
  and hostnames. It is saved in the private profile, returned by inspect/list
  and advertised as `direct.allow_insecure`; loopback HTTP remains implicit,
  and HTTPS certificate verification is unchanged. The client-mode
  `--allow-insecure` flag does not override a direct profile.
- **Homepage and companion.** The homepage is redrawn in ink on paper around
  topophany-bar's dithered globe, introduces the macOS menu bar companion and
  keeps the TUI's palette as plates for the replay, demo and web app. The
  favicon, Apple touch icon and social card use the same icon.

## Compatibility and upgrades

State schemas are unchanged from 1.5.0: topology schema 1, batch and snapshot
schema 3, checkpoint schema 2 for external data, monitor protocol 1 and
`direct.schema=1`. Existing topology and direct profiles remain valid.

Upgrade collectors before workers. A 1.5.1 worker can report delivery codes and
structured attempt fields that a 1.5.0 or earlier collector rejects as an
invalid heartbeat. A 1.5.1 collector accepts both old and new workers. Alias
grouping needs the collector and worker both upgraded, because enrollment
supplies the collector identity and alternate addresses; a worker with several
servers requires a collector that returns `collector_id`. A single-server
worker without aliases does not need to identify first.

`availability_scope` is a new topology field. Configuration decoding is strict,
so upgrade every collector, worker and viewer that reads the topology before
adding it; configurations without the field are unaffected. `allow_insecure` is
a new private direct field: upgrade the local binary before saving a profile
with it, and remove it or restore a backup before rolling that profile back to
an older binary. The option is not accepted from collector topology JSON.

Live sessions and their diagnostics are local to one binary and do not change
the monitor or viewer protocols. Session files live under the user cache
directory with 0700 directories and 0600 files; they hold no credentials,
samples, topology or request/response bodies.

Rollback to 1.5.0 does not require a state migration, but older binaries reject
topologies that use `availability_scope` and direct profiles that use
`allow_insecure`. Keep a matching configuration backup before upgrading.

## Acceptance scope

The automated suite covers sessions, service scopes, authenticated alias
grouping and failover, delivery diagnostics, connection rotation and per-source
direct HTTP consent through synthetic loopback endpoints and temporary
directories. It exercises identity pinning, receipt migration, failure
categorization, bounded telemetry, secret redaction, session leases and
confirmation recovery. CI and release builds require the real old-reader
compatibility test to execute and pass. Cross-builds verify compilation for
each target. No production deployment acceptance is claimed.

## Downloads

Choose `topophany_1.5.1_<os>_<arch>`: `.tar.gz` for Linux and macOS, `.zip` for
Windows. macOS is `darwin`; Apple silicon is `arm64`, and Intel or AMD 64-bit
systems are `amd64`. Each archive contains `topo` (`topo.exe` on Windows), the
license, the three READMEs and the changelog. `topo version` should report
`Topophany 1.5.1`. Source builds require Go 1.26.10 or newer.
