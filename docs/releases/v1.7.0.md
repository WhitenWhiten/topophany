# Topophany v1.7.0

Released November 14, 2026.

Topophany 1.7.0 adds Products mode, an Overview for people who ship a few apps
and sites, with `topo show products` and a `products.list` monitor metric to
read it from scripts and menu bars. It also adds an opt-in management control
plane for signed configuration delivery and official-release updates, which
stays off unless you enable it, and refines how the TUI lays out evidence,
server resources and service states. Verify downloads against
`SHA256SUMS.txt`.

## Changes since 1.6.0

- **Products mode.** `P`, `--mode products` or Settings → Overview turns the
  Overview into a board with a row for each part of each product a user
  reaches. Each row shows the part's state and what it rests on, from the
  edge in front to the platform or machine it runs on to its databases, each
  layer with its own mark, and its lead check's median latency, recent samples
  and share up. A part in trouble opens a row underneath with what failed,
  since when and from where, and the certificates soonest to expire stand at
  the foot. Products mode reaches no new conclusions: every mark on the board
  is one the network view already gives.
- **Products for scripts and widgets.** `topo show products [--json]` prints
  the board, and `products.list` in `topo monitor stream` carries it to
  widgets and menu bars, with each lead check's and certificate's own
  deadline. A `products.list` value may use up to 256 KiB of a frame.
- **Application kind.** An application may say what `kind` it is (`ios`,
  `web`, `api`, …). The kind labels the product and decides nothing.
- **Products template.** `topo templates products` writes a paused example of
  two iOS apps, a web app and a blog on Cloudflare Workers and Pages, a server
  of their own, Vercel and Supabase. The preview offers it a
  `certificate-expiring` scenario.
- **Opt-in management.** A separate control plane delivers signed, reviewed
  configuration to enrolled workers and collectors, and a separately installed
  Linux/systemd helper can move a node to an exact, signed official release
  with health checks and binary-only rollback. Configuration acceptance and
  update acceptance both default to off and are independent; existing viewer
  and worker credentials gain no management powers.
- **TUI refinements.** A service's evidence scope is laid out as marks and
  rows; server cards set network, swap and load beside the CPU, memory and
  disk panels; the status card says its availability coverage beside the big
  number; evidence panels keep their labels in one column; Services and Checks
  say what they are browsed by on the panel's edge; and a narrow card shortens
  a service's name rather than its state. `topo edit` forms widen for long
  labels.
- **Fixes.** A service is marked with its assessment's own state, so an
  unestablished availability is no longer a green `UNKNOWN` pill, and an open
  dialog's keys stay lit on the footer.

## Compatibility and upgrades

Existing 1.6.0 topologies, collector state, direct profiles and local stores
need no migration. Observation wire formats and default local monitoring
behavior are unchanged, and no management process, credential or listener is
installed or enabled by the upgrade.

**Upgrade collectors and workers before setting `kind`.** Older collectors
and workers refuse a topology file that sets an application's `kind`; older
viewers ignore it.

**Check the catalog before requesting `products.list`.** Widgets and menu bars
should look for the metric in `monitor stream --capabilities` before asking a
collector for it.

The `mode` preference saves which Overview opens. Network, the default, is
saved as no mode, so older binaries still read the preferences file.

Management requires explicit local opt-in and maintainer publisher setup;
see the [management guide](https://github.com/WhitenWhiten/topophany/blob/v1.7.0/docs/MANAGEMENT.md)
for its schemas, platform limits and the release baseline managed updates
need. Upgrades from earlier versions must also follow the
[1.6.0 upgrade guidance](https://github.com/WhitenWhiten/topophany/blob/v1.7.0/docs/releases/v1.6.0.md#compatibility-and-upgrades).

The macOS companion has a separate release lifecycle. This release publishes
the `topo` command-line binaries; companion UI support is version-dependent.

## Acceptance scope

Automated tests draw Products mode over the products example at every
terminal size and on every device the preview simulates, check that
`topo show products --json` is the board in every scenario the example offers,
and check that `products.list` fits its frame budget in every scenario of the
built-in network. Management tests
use isolated files, loopback TLS, synthetic credentials and signed fixtures;
see [Scenarios](https://github.com/WhitenWhiten/topophany/blob/v1.7.0/docs/SCENARIOS.md)
for the cases and their tests. No production publisher keys, signed GitHub
release or real fleet upgrade is claimed. Cross-builds establish compilation
for their targets, not production deployment or hardware acceptance.

## Downloads

Choose `topophany_1.7.0_<os>_<arch>`: `.tar.gz` for Linux and macOS, `.zip` for
Windows. macOS is `darwin`; Apple silicon is `arm64`, and Intel or AMD 64-bit
systems are `amd64`. Each archive contains `topo` (`topo.exe` on Windows), the
license, the three READMEs and the changelog. `topo version` should report
`Topophany 1.7.0`. Source builds require Go 1.26.11 or newer.
