# Topophany v1.6.0

Released November 12, 2026.

Topophany 1.6.0 adds a CF-Server-Monitor resource source for collector
topologies and direct profiles. Host checks and the Beszel, Komari and
CF-Server-Monitor adapters now report network rates, swap and load averages.
Source builds require Go 1.26.11, which fixes a standard-library HTTP server
vulnerability. Verify downloads against `SHA256SUMS.txt`.

## Changes since 1.5.4

- **CF-Server-Monitor source.** The read-only `cf-server-monitor` adapter
  reads CPU, memory, aggregate disk, network rates, swap and load from a
  CF-Server-Monitor Worker's `GET /api/server?id=<uuid>`. The mapping is pinned
  to upstream commit `612027c`. It keeps the Worker's `last_updated` as the
  sample time, so repeated reads keep the original deadline. Public Workers
  need no credential. Private Workers take a pre-issued JWT, sent as a Bearer
  token. Use `topo templates cf-server-monitor` for a paused collector
  topology, or `topo setup --task direct` for a collector-free TUI profile.
  Direct discovery verifies a configured JWT and lists at most 1,000 servers.
- **Host network, swap and load.** Host resource checks add optional facts for
  receive and transmit rates, swap capacity and usage, and 1, 5 and 15-minute
  load averages. A rate needs two consecutive counter samples from the visible
  non-loopback interfaces, which can include virtual interfaces. The first
  sample, an interface change or a counter reset starts a new baseline and
  reports no rate. Windows reports paging-file capacity and usage, and no load
  averages.
- **External network, swap and load.** Resource reports carry optional
  `network`, `swap` and `load` groups. Beszel maps `b`, `swap` and `la`, and
  falls back to its legacy `nr`/`ns` MiB/s rates and GiB swap. Komari maps
  `network`, `swap` and `load` from the recent report. CF-Server-Monitor
  converts the Agent's MiB swap to bytes. Missing and invalid readings keep
  their field status and never become zero. Out-of-range integers, negative
  zero and swap usage above capacity are invalid.
- **Servers page and monitor metrics.** The Servers page shows the new groups
  when the current reading has them. `server.card` carries them,
  `servers.list` entries carry them as `resource_metrics` with their own
  `sampled_at` and `valid_until`, and the catalog adds
  `resource.network.*`, `resource.swap.*` and `resource.load.*` node scalars
  with `host.*` counterparts for native host checks. These scalars use
  `visual: "text"`. A `servers.list` value may now use 256 KiB of a frame.
- **OrbStack adapter lab.** `scripts/accept_orbstack.py` runs seven adapters
  against real upstream software in disposable OrbStack containers. The
  containers have internal-only networking and no host mounts or published
  ports. The script checks that the macOS default route, DNS, proxy and
  interface list are unchanged after the run.
- **Go 1.26.11.** Source builds and release binaries use Go 1.26.11 to fix
  GO-2026-6859 in the standard-library HTTP server, which CI's `govulncheck`
  gate found.

## Compatibility and upgrades

Existing 1.5.4 topologies, collector state, direct profiles and local stores
need no migration. Topology schema 1, batch and snapshot schema 3, checkpoint
schema 2 for external data, monitor protocol 1, `direct.schema=1` and the local
configuration API schema 1 are unchanged. No existing measurement contract
changes. Detect the new adapter through `direct.adapters` in
`monitor stream --capabilities`, and the new metrics through its catalog.

**Upgrade collectors before workers.** A 1.6.0 worker includes `network`,
`swap` and `load` in Beszel and Komari resource reports whenever the upstream
supplies them. A 1.5.4 collector does not know those keys and refuses the whole
batch. Host check facts need no collector upgrade, because collectors already
accept them as ordinary facts.

**Upgrade viewers with the collector.** A 1.5.4 viewer still reads snapshots
from a 1.6.0 collector but does not show the new readings. It refuses the
history of an external check whose stored samples carry the new groups.

Upgrade every role before you add a `cf-server-monitor` source to a topology,
and upgrade the local binary before you add one to a direct profile. Older
binaries reject the adapter name.

Rolling back to 1.5.4 needs no schema conversion, because the schema numbers
are unchanged. Remove `cf-server-monitor` sources first, then roll back workers
before the collector. A 1.5.4 collector decodes stored state leniently and
would not serve the new readings. No test runs a 1.5.4 collector on 1.6.0
state, so keep a collector backup from before the upgrade. Binaries built with
a Go version older than 1.26.11 remain exposed to GO-2026-6859. Upgrades from
earlier versions must also follow the
[1.5.4 upgrade guidance](https://github.com/WhitenWhiten/topophany/blob/v1.6.0/docs/releases/v1.5.4.md#compatibility-and-upgrades).

The macOS companion has a separate release lifecycle. This release publishes
the `topo` command-line binaries; companion UI support is version-dependent.

## Acceptance scope

Automated tests use loopback Worker endpoints, synthetic upstream responses,
injected host counters and parser fixtures. They cover the CF-Server-Monitor
request path and authentication, unit conversion and invalid readings, sample
time retention through the worker, collector and monitor, and direct setup and
polling. They also cover network rate baselines, report normalization,
per-adapter field statuses and the `servers.list` frame budget. The
CF-Server-Monitor resource decoder has a fuzz target.

The OrbStack lab exercises Beszel 0.21.0, Komari 1.6.0, the CF-Server-Monitor
Worker at `612027c` with Go Agent 1.1.3, Mihomo 1.19.33, WireGuard, Tailscale
1.90.9 with Headscale 0.29.7, and cloudflared 2026.10.5 inside one disposable
Linux VM. It does not cover cloudflared's connected-edge path, Cloudflare
account APIs or public DERP relays, and its host metrics describe the lab VM.
No real-account CF-Server-Monitor deployment or other upstream versions are
claimed. Cross-builds establish compilation for their targets, not production
deployment or hardware acceptance.

## Downloads

Choose `topophany_1.6.0_<os>_<arch>`: `.tar.gz` for Linux and macOS, `.zip` for
Windows. macOS is `darwin`; Apple silicon is `arm64`, and Intel or AMD 64-bit
systems are `amd64`. Each archive contains `topo` (`topo.exe` on Windows), the
license, the three READMEs and the changelog. `topo version` should report
`Topophany 1.6.0`. Source builds require Go 1.26.11 or newer.
